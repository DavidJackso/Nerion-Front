01

Архитектура и многоарендность

Ядро Nerion — генератор выходов. Пользователь один раз описывает данные внутри «пространства»; платформа автоматически отдаёт их в виде REST API, публичных списков и PDF. Серверная часть обязана поддерживать произвольные пользовательские схемы данных без выкатки кода.

Изоляция арендатора

Каждое пространство — отдельная схема PostgreSQL. Таблицы пользователя создаются как реальные таблицы внутри схемы пространства. Кросс-схемные запросы запрещены.

Динамический DDL

Создание/изменение «таблицы» пользователя транслируется в CREATE / ALTER TABLE внутри схемы. Системный реестр хранит метаописание полей.

Бизнес-язык

API и UI оперируют доменными словами (Курс, Клиент), не SQL. Сервер хранит соответствие «человеческое имя ↔ slug ↔ физическая колонка».

Выходы из одной модели

REST, списки и PDF читают одну и ту же модель данных. Изменение схемы немедленно отражается во всех выходах.

FR‑1.1

Must Системная БД хранит реестр: пользователи, пространства, участники, метаописание таблиц и полей, API-ключи, PDF-шаблоны, маппинги, задачи генерации, журнал.

FR‑1.2

Must При создании пространства сервер создаёт изолированную схему PostgreSQL и фиксирует её slug. Slug уникален в пределах инсталляции, неизменяем после создания.

Slug — латиница, цифры, дефис; используется в URL API и публичных списков.

FR‑1.3

Must Данные одного пространства недоступны из контекста другого. Авторизация проверяется на уровне пространства до любого обращения к его схеме.

FR‑1.4

Should Каждое изменение схемы версионируется (миграция с меткой времени и автором) для отката и аудита.

02

Аутентификация и сессии

Экраны A01 Вход · A02 Регистрация · A03 Сброс пароля · A04 Новый пароль. Сессии на JWT.

FR‑2.1

Must Регистрация по email + пароль. Email уникален, проверяется подтверждающим письмом со ссылкой ограниченного срока действия.

FR‑2.2

Must Пароли хранятся только в виде хэша (bcrypt/argon2). Минимальная длина и базовая проверка стойкости — на сервере, не только на клиенте.

FR‑2.3

Must Вход выдаёт пару токенов: короткоживущий access (JWT) и долгоживущий refresh. Refresh отзывается при выходе и смене пароля.

FR‑2.4

Must Сброс пароля: запрос по email → одноразовая ссылка с токеном (срок ≤ 60 мин) → установка нового пароля. После использования токен инвалидируется, все активные сессии завершаются.

FR‑2.5

Should Ограничение частоты попыток входа и запросов сброса по IP и по аккаунту (защита от перебора).

03

Пространства

Экраны SP01 Список · SP02 Создание. Пространство — единица аренды, изолированная схема данных.

FR‑3.1

Must Пользователь видит список только тех пространств, где он участник. Для каждого — имя, slug, роль пользователя, статус API, число таблиц.

FR‑3.2

Must Создание пространства: имя + slug. Создатель становится Admin. Сервер инициализирует схему БД (FR‑1.2) и базовый API-ключ.

FR‑3.3

Must Удаление пространства необратимо: удаляются схема, данные, ключи, шаблоны, файлы. Требуется подтверждение вводом имени пространства.

FR‑3.4

Should Лимит числа пространств и таблиц на аккаунт согласно тарифу (проверяется на сервере при создании).

04

Команда и роли

Экран SET02. Две роли внутри пространства.

Admin

Полный доступ: схема, API-ключи, команда, настройки, биллинг, удаление пространства.

Member

Работа с данными и генерация PDF. Нет доступа к схеме, ключам, команде и удалению.

FR‑4.1

Must Admin приглашает участника по email. Приглашённый, если не зарегистрирован, проходит регистрацию по ссылке и автоматически добавляется в пространство с назначенной ролью.

FR‑4.2

Must Сервер обеспечивает разграничение прав по ролям на каждом защищённом эндпоинте. Member не может вызвать операции схемы/ключей даже напрямую через API.

FR‑4.3

Must Admin меняет роль и исключает участников. Нельзя удалить или понизить последнего Admin пространства.

05

Схема: таблицы и поля

Экраны SCH01 Список таблиц · SCH02 Выбор шаблона · SCH03 Редактор полей · SCH04 Настройки таблицы. Это ядро продукта: пользователь описывает данные, сервер материализует схему.

FR‑5.1

Must Создание таблицы: имя (домен-язык), slug. Сервер создаёт физическую таблицу в схеме пространства с системными полями id, created_at, updated_at.

FR‑5.2

Must Таблица может создаваться из шаблона (SCH02): набор предзаданных полей под типовой сценарий (напр. «Курс», «Преподаватель», «Клиент»). Шаблон — стартовый набор, поля затем редактируются.

FR‑5.3

Must Поддерживаемые типы полей: текст, длинный текст, число, дата, дата-время, логический, выбор из списка (enum), email, телефон, ссылка, файл, связь с другой таблицей.

Каждый тип поля → корректный тип колонки PostgreSQL + правила валидации.

FR‑5.4

Must Атрибуты поля: имя, slug, тип, обязательность, значение по умолчанию, уникальность, для enum — список значений, для связи — целевая таблица и кардинальность.

FR‑5.5

Must Изменение полей (добавить/переименовать/изменить тип/удалить) транслируется в безопасную миграцию. Несовместимая смена типа (напр. текст→число с непреобразуемыми данными) отклоняется с понятной ошибкой.

FR‑5.6

Must Связи между таблицами реализуются внешними ключами в пределах схемы пространства. При удалении целевой записи — поведение по правилу связи (запрет / обнуление).

FR‑5.7

Must Удаление таблицы (SCH04) необратимо удаляет физическую таблицу и данные; затрагивает зависящие выходы (API-маршруты, списки, маппинги PDF) — сервер предупреждает о зависимостях.

FR‑5.8

Should Slug поля и таблицы неизменяем после первой публикации в API (ломает интеграции); переименование меняет только человеческое имя.

06

Записи и данные

Экраны D01 Таблица записей · D02 Создание · D03 Редактирование · D04 Удаление. Стандартный CRUD по динамической схеме с серверной пагинацией, сортировкой, фильтром и поиском.

FR‑6.1

Must Чтение записей с серверной пагинацией (limit/offset или курсор), сортировкой по любому полю и фильтрами по полям. Поиск по текстовым полям.

FR‑6.2

Must Создание и редактирование валидируют значения по схеме поля (тип, обязательность, уникальность, диапазон enum). Ошибки возвращаются по полям.

FR‑6.3

Must Удаление записи (D04) с подтверждением. Поддержка пакетного удаления выбранных записей.

FR‑6.4

Should Импорт записей из CSV/XLSX с сопоставлением столбцов полям и отчётом об ошибках построчно. Экспорт текущей выборки в CSV.

FR‑6.5

Should Поля-связи при чтении возвращают читаемое представление связанной записи (а не только id).

07

Авто-REST API и Swagger

Экраны API01 Обзор · API03 Swagger. Главный выход продукта: каждая таблица немедленно доступна как публичный REST-ресурс с авто-документацией.

FR‑7.1

Must Для каждой таблицы автоматически генерируются CRUD-эндпоинты по slug пространства и таблицы. Никакой ручной выкатки кода — маршрутизация динамическая.

FR‑7.2

Must Публичный API авторизуется по API-ключу (заголовок). Ключ привязан к пространству и определяет доступ только к его данным.

FR‑7.3

Must Сервер автоматически отдаёт OpenAPI/Swagger-спецификацию пространства, отражающую текущую схему. Изменение полей мгновенно обновляет спецификацию.

FR‑7.4

Must Экран API01 показывает статус каждого ресурса (online / setup / offline), базовый URL и список эндпоинтов с методами. Статусы вычисляются сервером.

FR‑7.5

Should Ограничение частоты запросов на ключ и счётчик использования (для тарифов и метрик).

08

API-ключи

Экран API02. Управление ключами доступа к публичному API пространства.

FR‑8.1

Must Admin создаёт именованные ключи. Полное значение ключа показывается один раз при создании; далее хранится и отображается только префикс. На сервере хранится хэш.

FR‑8.2

Must Ключ можно отозвать (немедленно перестаёт работать). Для каждого ключа: имя, префикс, дата создания, последнее использование, статус.

FR‑8.3

Should Область действия ключа: только чтение или чтение+запись.

Безопасность Ключ показывается один раз («Сохрани ключ — он показывается один раз»). Сервер не хранит и не может восстановить открытое значение — только хэш и префикс для идентификации.
09

Публичные списки (выходы)

Группа экранов FILES. Опубликованные списки — выход, который фронтенд клиента забирает по slug, без знания внутренних id и без хардкода схемы.

FR‑9.1

Must Пользователь публикует выборку из таблицы как именованный список с собственным slug. Список читается публично по slug без API-ключа (или по публичному режиму, настраиваемому).

FR‑9.2

Must Конфигурация списка задаёт: исходную таблицу, набор и порядок отображаемых полей, фильтр, сортировку, лимит. Ответ отдаёт только выбранные поля под их публичными именами.

FR‑9.3

Must Публичный ответ стабилен по контракту: фронтенд обращается по slug списка, а не по физическим идентификаторам. Переименование внутренних полей не ломает публичный список, пока его конфигурация сохраняет публичные имена.

FR‑9.4

Should Кэширование публичных ответов с инвалидацией при изменении данных или конфигурации. Поддержка CORS для чтения с произвольных доменов.

FR‑9.5

Should Список можно снять с публикации (перестаёт отвечать) без удаления данных.

Эндпоинты

МетодПутьНазначение
GET/spaces/{slug}/listsСписок опубликованных списков
POST/spaces/{slug}/listsОпубликовать список
PUT/spaces/{slug}/lists/{listSlug}Изменить конфигурацию / снять с публикации
GET/lists/{space}/{listSlug}Публичное чтение по slug
Принцип «Без id и без хардкода»: клиентский фронтенд должен уметь рисовать список, зная только его slug и публичные имена полей из ответа. Это позволяет менять данные и схему на стороне Nerion, не выкатывая клиента.
10

Генерация PDF по ГОСТ

Экраны PDF01 Шаблоны · PDF02 Маппинг полей · PDF03 Предпросмотр (+ одиночная и пакетная генерация, архив). Второй ключевой выход: документы, которые принимает регулятор.

FR‑10.1

Must Пользователь загружает шаблон документа (DOCX) с плейсхолдерами. Сервер разбирает шаблон и извлекает список плейсхолдеров для маппинга.

FR‑10.2

Must Маппинг (PDF02): каждому плейсхолдеру шаблона сопоставляется поле таблицы или вычисляемое выражение. Маппинг сохраняется и переиспользуется.

FR‑10.3

Must Генерация: сервер подставляет данные записи в шаблон и рендерит PDF (Python + WeasyPrint) с сохранением форматирования по ГОСТ. Предпросмотр (PDF03) показывает результат до выпуска.

FR‑10.4

Must Пакетная генерация: один шаблон × выборка записей → набор PDF (по файлу на запись или единый сшитый документ). Выполняется асинхронной задачей с прогрессом и статусом.

FR‑10.5

Must Сгенерированные документы складываются в архив пространства: имя, шаблон, источник, дата, автор, ссылка на скачивание. Файлы хранятся в Object Storage.

FR‑10.6

Should Статус шаблона (готов / требует маппинга / ошибка) вычисляется сервером и отражается на PDF01.

11

Файлы и хранилище

Файловые поля записей, загружаемые DOCX-шаблоны и сгенерированные PDF хранятся в Yandex Object Storage.

FR‑11.1

Must Загрузка файлов через сервер с проверкой типа и размера. Файлы изолированы по пространству; путь не должен раскрывать данные другого арендатора.

FR‑11.2

Must Доступ к приватным файлам — по подписанным временным ссылкам. Публичные выходы (списки) отдают файлы согласно режиму публикации.

FR‑11.3

Should При удалении записи/таблицы/пространства связанные файлы помечаются на удаление и очищаются фоновой задачей.

12

Настройки и аккаунт

Экраны SET01 Настройки пространства · SET03 Аккаунт.

FR‑12.1

Must Admin меняет имя пространства и параметры. Danger zone — удаление пространства с подтверждением вводом имени (FR‑3.3).

FR‑12.2

Must Пользователь меняет имя, email (с переподтверждением) и пароль (с инвалидацией прочих сессий).

FR‑12.3

Should Удаление аккаунта: запрет, пока пользователь — единственный Admin непустого пространства; иначе передача прав или удаление пространства.

Журнал и аудит

FR‑12.4

Should Сервер ведёт журнал значимых действий (вход, изменение схемы, выпуск/отзыв ключа, генерация PDF, удаление) с автором и временем — для аудита и поддержки.

13

Нефункциональные требования

Безопасность

HTTPS везде; хэш паролей и ключей; защита от SQLi при динамическом DDL (белый список идентификаторов, параметризация); RBAC на каждом эндпоинте; rate limiting.

Изоляция данных

Жёсткая многоарендность: схема-на-пространство, проверка принадлежности до доступа к схеме, отсутствие кросс-схемных запросов.

Производительность

Чтение списка ≤ 300 мс при 10 тыс. записей; серверная пагинация; индексация по сортируемым/фильтруемым полям.

Асинхронность

Пакетная генерация PDF и тяжёлые миграции — фоновые задачи с очередью, статусом и повторами.

Надёжность

Ежедневный бэкап БД и Object Storage; транзакционность DDL+метаданных (откат при сбое миграции); идемпотентность создающих операций по ключу запроса.

Наблюдаемость

Структурные логи, метрики (запросы API на ключ, время рендера PDF), алёрты на ошибки 5xx и упавшие задачи.

Совместимость

Стабильный контракт публичного API и списков; неломающие изменения схемы версионируются; slug-идентификаторы неизменяемы после публикации.

Локализация

Серверные сообщения об ошибках — на русском, в тоне продукта; коды ошибок машинно-читаемы для клиента.

Формат ошибок

{
  "error": {
    "code": "validation_failed",
    "message": "Проверь поля и попробуй ещё раз.",
    "fields": {
      "hours": "Должно быть числом"
    }
  }
}

Открытые вопросы к ревью

  • Тарифные лимиты: точные значения по числу пространств, таблиц, записей, запросов API и объёму хранилища.
  • Режим публичных списков: всегда публичны или с публичным токеном? Нужен ли троттлинг анонимного чтения.
  • Связи таблиц: ограничиться связью «один-ко-многим» в MVP или сразу «многие-ко-многим».
  • Версионирование публичного API при изменении схемы — нужен ли явный номер версии в пути.
  • Биллинг и вебхуки — вне этого документа; уточнить точку интеграции.
